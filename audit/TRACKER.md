- **Iter 14 continued (server/src/middleware/auth.ts):** read the full file (`protect`, `authorize`, `optionalAuth`, token generation). Found and fixed a CRITICAL bug: `protect` fetches the user fresh from the DB specifically to check `isActive`, but then built `req.user` from the JWT payload's `decoded.role`/`decoded.email` instead of the freshly-fetched `user.role`/`user.email` — meaning a role change made via the admin Users panel (promote or demote) had zero effect on that user's already-issued access token until it naturally expired (up to `JWT_EXPIRES_IN`, default 7 days). A superadmin demoting a compromised or terminated admin account would NOT actually revoke their admin API access in real time — only deactivating the account (`isActive: false`, which IS freshly checked) would. Fixed by using `user.role`/`user.email` instead of `decoded.role`/`decoded.email`. Found and fixed a real bug spanning 3 functions in server/src/controllers/orderController.ts: `cancelOrder` (customer-facing), `updateOrderStatus` (admin single), and `bulkUpdateOrderStatus` (admin bulk) all correctly restored product stock when an order was cancelled/returned, but none of them touched `Coupon.usedCount` — only the rarely-used hard-delete path (`deleteOrder`) did. Fixed by adding `Coupon.findOneAndUpdate({code: order.coupon}, {$inc: {usedCount: -1}})` alongside the stock-restore in all three cancel paths, and the symmetric `+1` in `updateOrderStatus`'s reactivation branch (cancelled/returned → active status).
